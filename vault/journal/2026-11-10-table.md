# 2026-11-10: table (L6, A4, G5)

Leg `a2ui/table`, in Q-0002's answered shape: `<table>` with `<col>`s
declared once and rows that are `item`s. It replaces nothing on main (the
2026-11-07 branch's `table`/`tablehead`/`tablerow`/`cell` never landed);
its look is that branch's, which Design reviewed on 2026-11-07: a header
muted at weight 400 with one rule beneath, a list's selection and marker,
row hairlines only while no row is selected, muted sort chevrons (ink on
the sorted column). Its tags are not.

## What it is

- **`surfui.Table(kids...)`** takes `Col`s, `Item`s, an `Empty` and a foot
  (any other kid), and builds a `div.u-stack.u-table` of the header row
  (`u-thead`), a rule, the body (a `List`, `u-table-body`), and the foot.
  Each cell of a row is wrapped in a `Row` (`u-cell`) of its column's
  width, with a `Spacer` before it for `end` and both sides for `center`.
  Assembly is pure over the kids as given (a row is copied before its
  cells go in), so `Table.Add` builds it again: the Go builder pattern
  `t.Add(row)` still works.
- **Widths are fixed when the tree is resolved** (`resolveTable`, from
  `resolve`), not when the table is built, because the density isn't
  known until the root has it. An `auto` column is as wide as its widest
  cell, heading included, from `surfui.NaturalWidth`, a copy in surfui of
  what the cells' layout gives a text, chip, glyph, key, button, line and
  row (`TestTableMeasureIsTheLayouts` holds the two together, at Dense
  and Compact, in pkg/cells, which can import both). The result is the
  cell's `--u-w` (the host's `ch`, the cells' width): the same number on
  both sides, so they cut in the same place. `max="40%"` is `--u-maxp`:
  the host's `max-width: N%`, the cells' share of the row (`box.maxp`,
  taken in `widths`). `fill` is `u-grow`. An `auto` cell is `u-shrink`: a
  basis that gives way where the row is too narrow (`fShrink`).
- **`:if` on a `col` is the attribute `show`** (compile.go): the column
  stays in the table, hidden, so that a row's cells keep their places and
  the cell of a hidden column goes with it. A cell given an `:if` shifts
  the cells after it; the docs say so.
- **`@activate` on an `item`**: a click on the selected row, a double
  click (`Count >= 2`), both after the row's own `@click`
  (`surfrun.Surface.event`); and Enter, which the table binds on its body
  as `surfui.Activation{Act, Value}` where its selected row has one
  (`Surface.bound` runs it with the row's key). The body then takes the
  keyboard. `data-on` asks the host for clicks for an item with only an
  `@activate`.
- **`scroll` goes to the body, `height` is the whole table's** (so the
  body takes what the header and foot leave, as any `scroll` box does in
  a fixed stack). The cells' scroll box already has the bar (`│` track,
  `┃` thumb in the last column) and keeps the selected row in view; the
  header leaves the bar's column (`u-table-scroll` on the table).
- **`$range`** is a load error outside a table; inside, it is
  `surfui.RangeMark` in the text, which `resolveTable` writes over, as
  `F–L of N`. The tree can only know the window from the selection, which
  is the least scroll from the top that holds the selected row, so on a
  host that is an estimate (the host can't tell where its box is
  scrolled: hotty's `view` event reports elements, not offsets). The
  cells say it exactly: `painter.leaf` fills the template with what
  `Renderer.tableRange` reads from the body's box and offset.
  **This is the one place the two renderings differ**, and it is a
  question for the maintainer (below).
- **`tr`/`th`/`td`/`thead`/`tbody`** are read in a `table` only
  (`tableAliases` in table.go, markup to markup before the widget is
  made), as columns, `item`s and `line`s; a Markdown table converts one
  to one. A `th` row in the body becomes a semibold `line`. They are no
  widgets (a load error elsewhere).
- Vocabulary: `table`, `col` (text), `empty`; on `col`: `width` (a
  string: cells, `auto`, `fill`), `fill`, `max`, `align`, `sort`, `show`
  (placed first in Attrs so they win over the generic `width` int and
  `fill` tone). `item` gains the event `activate`.

## For the maintainer, and the gaps

- **`$range` on a host is an estimate.** Options: (a) as it is: exact in
  the cells (margin's own rendering), the window the selection implies
  on a host; (b) a host reports its scroll through `view` events on the
  rows, and the surface re-renders the range: exact, M more work and a
  frame per scroll; (c) the framework windows the rows itself (draws
  only `height` of them, from the selection), so the range is always
  exact and no scroll box is needed, but a host's wheel does nothing and
  the scrollbar is the framework's. I chose (a) and said so in the docs.
- **The scrollbar's room on a host.** The cells reserve the bar's column
  and the header leaves it. A host's `scrollbar-width: thin` bar takes
  room only where the rows overflow, in an engine that draws one; the
  header there has no matching room, so a right-aligned column can sit
  a few px off between header and rows when the rows scroll. Not proven
  either way (neither engine draws a scrollbar in a still render); not
  worked around.
- **The CSS** the table is the first to use: `max-width: calc(var(--u-maxp)
  * 1%)` on a flex child, `flex: 0 1 auto` over a `width`, `overflow:
  hidden` on a row, and a bottom `linear-gradient` layer for the hairlines
  (an inset `box-shadow` followed the row's rounded corners: seen in the
  first shots, in both engines).
  css-subset.md lists them with what the gate shows.
- Selection: the keyboard is the model's, as the brief says (`<bind>`
  on the table); only Enter is the table's, and only where a row has an
  `@activate`.
- The regression tests were written with the feature and not seen failing
  first (the behaviour had no earlier form to fail on).
